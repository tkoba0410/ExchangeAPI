# Stage8: Hardening for Multi-Exchange Expansion

## 目的（Why Stage8 exists）

Stage8 は、次ステージ（Stage9 以降）で **3つ目以降の取引所を追加する** ことを前提に、以下の **2つの近接した目的** を同時に達成するための設計・構成調整ステージです。

1. **Stage7 までに構築した設計・実装を煮詰め、揺れを止めること**
2. **将来の取引所追加が、設計判断ではなく“作業量”の問題に還元される構成に整えること**

Stage8 は新機能追加のためのステージではありません。既存構造を検証材料として使い切り、
「この構成で本当に横に増やせるか」を確認・固定するための最終調整フェーズです。

---

## 到達点（Stage7 まで）

Stage7 までに、本プロジェクトは以下の前提を獲得しています。

- Spot-only API に限定した最小共通集合の確立
- Transport を除く **全層 Call-only 方針** の確定
- Raw / Normalized / Adapter / Contracts / Domain の責務分離
- Bitflyer / Bittrade の2取引所による実装検証

これにより「2取引所対応のAPI」は完成していますが、
同時に **2取引所で止まっている設計** も残っています。

---

## Stage8 が解決する問題

Stage8 では、次の問いに明確な答えを与えることを目的とします。

- 3つ目の取引所を追加するとき、**どこが必ず痛むのか**
- その痛みは、**設計の曖昧さ**なのか、**不可避な取引所差分**なのか
- 共通化しない判断は、**構造（型・層・名前）として固定**されているか

Stage8 は「共通化を進める」ステージではなく、
**共通にできないものを含めて設計を確定させる** ステージです。

---

## 基本方針

### 1. 新しい取引所は追加しない

Stage8 では **新規取引所を追加しません**。

既存の Bitflyer / Bittrade のみを材料として、

- 差分の洗い出し
- 責務の押し戻し
- 横断契約の明文化

を行います。

---

### 2. 横断契約を“硬化”させる

3つ目以降の取引所追加で最も破綻しやすいのは、横断概念の曖昧さです。

Stage8 では特に以下を重点的に固定します。

- Limit / Cursor / Page / PageMeta の契約
- Call / CallMeta / RawJson / ClosedSet の責務境界
- 未対応・仕様差分・制約条件の表現方法

これにより、将来の取引所追加時に「同じ壊れ方」を保証します。

---

### 3. 既存2取引所をテンプレートとして完成させる

Bitflyer / Bittrade を、

- フォルダ構成
- 命名規則
- レイヤーごとの責務
- Endpoint 一覧の粒度

の観点で揃えます。

目的は美しさではなく、**3つ目の取引所を“なぞれる”こと**です。

---

## 非目的（Anti-Goals）

Stage8 では、以下を目的としません。

- すべての取引所差分を共通化すること
- API 表現を完全に統一すること
- 理想的な最終形をこの段階で設計すること

Stage8 の目的は、現実の差分を抱えたままでも
横に増やせる構造を確定させることにあります。

---

## 設計劣化の兆候（Red Flags）

以下が発生した場合、Stage8 の前提が崩れている可能性があります。

- 新しい取引所追加時に Normalized 層の修正が必要になる
- Adapter 以外の層に exchange 固有分岐が増える
- Limit / Cursor / Page の扱いが取引所ごとに異なる説明を要する
- 「この取引所だけ特別」という説明が README に書けなくなる

これらは Stage8 に立ち戻って再検討すべきサインです。

---

## Stage8 の作業見通し（What will be done）

Stage8 の作業は、概ね次の流れで進みます。

1. **差分の棚卸し**
   - 2取引所間の構造・契約・表現差分のリスト化

2. **横断契約の整理・固定**
   - Page / Limit / Cursor
   - CallMeta / RawJson / Closed

3. **テンプレート化の完了**
   - 既存2取引所の構造・命名・責務を揃える

4. **追加手順の自明化**
   - 3つ目の取引所を追加する際の擬似手順・チェックポイントの明文化

---

## 参考: 新規取引所追加時の最初の流れ（概要）

1. 公式 API 文書を正本として Endpoint 一覧を作成する
2. Raw API を Call-only で実装する
3. Normalized 層で既存共通型へ写像する
4. Adapter 層で取引所差分を吸収する
5. Limit / Cursor / Page 契約をテストで確認する

---

## Stage8 で行わないこと

- 新規 API 機能の追加
- 新規取引所の実装
- 大規模なドメイン再設計
- Transport 層の仕様変更

---

## 完了条件（Definition of Done）

Stage8 の完了は、以下が満たされた時点とします。

- 3つ目の取引所追加手順が **設計的に自明** になっている
- 既存2取引所間に **構造的な歪み** が残っていない
- 共通化しない判断が README / Docs / 型構造から読み取れる
- Stage9 以降の作業が、設計ではなく **実装量の問題** に還元されている

---

## 次ステージへの接続

Stage9 以降では、Stage8 で確定した構造を前提に、

- 新規取引所（3つ目以降）を検証材料として追加
- 構造の妥当性を実装で再確認

を行います。

Stage8 はそのための **最後の設計固定ステージ** です。
