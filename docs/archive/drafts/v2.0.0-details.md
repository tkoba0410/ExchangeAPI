# ExchangeAPI v2.0.0 Draft Details

最終更新: 2026-04-22  
位置づけ: draft  
対応する概要版: [`v2.0.0-overview.md`](./v2.0.0-overview.md)

## 1. 位置づけ

本書は、`v1.0.0` 以後に進める `v2.0.0` ブラッシュアップ phase の詳細検討用ドラフトである。  
`v2.0.0` では破壊的変更を許容し、現行 public surface・型契約・責務分割・検証運用の再整理を行う。

設計正本は現時点では引き続き [`docs/spec.md`](./spec.md) とし、本書は `v2.0.0` に向けた論点整理と変更方針のたたき台として扱う。

## 2. 背景

- `v1.0.0` は現行 baseline として固定する
- 現行 repo には library / CLI / MCP Server の基盤がある
- 以後の phase では exchange 追加よりも品質・整合性・保守性を優先したい
- そのため、互換性維持を最優先とするより、次の基準点として自然な `v2.0.0` surface を作る方が合理的である

## 3. v2.0.0 の主目標

### 3.1 Public API の再整形

目標:

- 利用者が surface を追いやすい構造にする
- endpoint module ごとの差を減らす
- `Factory`, facade, request, response, option の責務を明瞭にする

主な論点:

- `*CallAsync(...)` の命名規約はこのままでよいか
- `Protocol` と `Native` で method / return contract の見え方が揃っているか
- 生成導線が `CreateXxxClient()` に寄りすぎていないか
- `public` と `private` の surface 切り方が利用者に直感的か

候補:

- 不自然な facade 名の rename
- request / option の統合または分離
- internal helper の public 漏出見直し
- future `Unified` を阻害する surface の除去

### 3.2 Error / Observation 契約の見直し

目標:

- エラー分類を利用者視点で理解しやすくする
- 障害時の解析コストを下げる
- raw body / status / venue error の観測境界を明確にする

主な論点:

- `CallError.Kind` の分類粒度は妥当か
- `Http` と `Semantic` の境界が一貫しているか
- codec failure に必要な文脈情報は足りているか
- logging / debug artifact と秘匿要件が両立しているか

候補:

- `CallError` payload の拡充
- venue 依存の error body 観測語彙の整理
- debug logging contract の再設計
- adapter での error rendering 統一

### 3.3 型契約の再評価

目標:

- nullable と required の意味を揃える
- scalar の解釈揺れを減らす
- 暗黙の string ベース表現を減らす

主な論点:

- decimal / quantity / price / amount の型境界
- timestamp の timezone / precision / wire format
- symbol / product code / market category の語彙整理
- enum 化すべき語彙と string のままにすべき語彙

候補:

- scalar contract の厳格化
- value object 導入可否の再評価
- DTO の nullability 是正
- decode 時の validation stage 再整理

### 3.4 物理構成と依存規約

目標:

- repo の構成理由を説明しやすくする
- 層の責務が directory / project にも反映されるようにする
- 将来変更時の局所性を上げる

主な論点:

- project 数と責務分割の粒度
- `Protocol` / `Native` / `Vocabulary` / `Composition` の依存方向
- adapter から exchange 実装への参照経路
- test project の粒度と配置

候補:

- project 再編
- namespace / path 規約の再定義
- architecture enforcement test の拡充
- 配線専用コードの隔離

### 3.5 Adapter 体験の整合

目標:

- CLI / MCP / library 間の言葉と挙動をできるだけ揃える
- 利用者が adapter 固有概念ではなく library 概念で理解できるようにする

主な論点:

- command 名や option 名と library endpoint 名の対応
- summary / pretty 出力と raw 出力の責務境界
- adapter の error 表示が `CallError` 契約を正しく反映しているか
- parity test が実使用を十分に代表しているか

候補:

- CLI command surface の rename
- MCP tool 名や引数名の見直し
- adapter 共通 formatting 層の整理
- parity test の再定義

### 3.6 テスト戦略の再編

目標:

- 回帰防止に効く test 構成へ寄せる
- live test の不安定さを局所化する
- `v2.0.0` 非互換点を意図どおり固定する

主な論点:

- unit / contract / live / parity の役割分離
- どの層で何を固定するか
- endpoint ごとの golden 的検証が必要か
- flaky test や rate limit 影響の扱い

候補:

- test taxonomy の整理
- live test opt-in 条件の再確認
- 変更検知しやすい assertion への置換
- migration risk を拾う test の追加

### 3.7 ドキュメントと移行

目標:

- `v1.0.0` 利用者が `v2.0.0` へ移りやすいようにする
- 設計判断と破壊的変更の理由を追跡可能にする

主な論点:

- 正本とガイドの責務分担
- `Overview`, `Spec`, `Migration Guide`, `Release Note` の切り分け
- rename / remove / merge / split の見せ方
- deprecated 期間を設けない場合の補助資料

候補:

- `v2.0.0` migration guide
- breaking changes ledger
- README 導線更新
- adapter ごとの getting started 再構成

## 4. 非ゴール

- `v2.0.0` 期間中に対応取引所をむやみに増やすこと
- `Unified` を拙速に実装すること
- public surface の違和感を残したまま互換性だけ守ること
- 破壊的変更の理由を文書化せず進めること

## 5. 判断基準

`v2.0.0` の変更判断は、少なくとも次を満たすものを優先する。

- 利用者にとって理解しやすくなる
- 将来の拡張余地が広がる
- 実装責務がより自然に分離される
- 観測性または検証可能性が向上する
- migration guide で説明可能である

## 6. 初期バックログ案

### Must

- breaking change 候補の列挙
- public API の rename / remove / reshape 候補の洗い出し
- error contract の再点検
- 型契約の nullability / scalar 見直し
- migration guide の素案作成

### Should

- CLI / MCP parity の再整理
- test taxonomy の文書化
- getting started の再構成
- architecture enforcement の拡充

### Nice to Have

- 将来 `Unified` を見据えた cross-venue 語彙整理
- debug artifact の再編
- internal tooling / codegen 補助の検討

## 7. 次アクション案

1. `v1.0.0` 現行 surface の違和感を列挙する
2. breaking changes を `rename / remove / split / merge / contract tighten` に分類する
3. 影響が大きいものから `docs/spec.md` への反映方針を決める
4. test と adapter に波及する変更を並行して棚卸しする
5. `v2.0.0` migration guide の skeleton を作る
