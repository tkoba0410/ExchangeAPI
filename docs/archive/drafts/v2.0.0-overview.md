# ExchangeAPI v2.0.0 Draft Overview

最終更新: 2026-04-22  
位置づけ: draft

## 1. 目的

本書は、`v1.0.0` を公開固定点とした後に進める `v2.0.0` 向けブラッシュアップ方針の概要版である。  
この phase では、取引所追加よりも既存 surface の再整理、契約の明確化、利用者体験の改善を優先する。

`v2.0.0` では破壊的変更を許容する。  
ただし、無秩序に壊すのではなく、`v1.0.0` 時点で残っている歪みや暫定判断を計画的に解消するための変更として扱う。

## 2. この phase の基本方針

- 取引所追加は主目的にしない
- `v1.0.0` で残した設計上の違和感を是正する
- `Protocol` / `Native` / `Adapter` の責務境界を再点検する
- public surface のわかりやすさと一貫性を優先する
- 破壊的変更は migration 可能性を意識して整理する

## 3. 主な検討領域

### 3.1 Public API 再設計

- facade / factory / request / response の命名と責務を整理する
- endpoint ごとの surface 差異を減らす
- 利用者が IDE 補完から理解しやすい形へ寄せる

### 3.2 Error / Observation 契約

- `Call`, `CallError`, `CallMeta` の語彙を見直す
- 障害解析に必要な情報量と秘匿境界の両立を図る
- `Http` / `Codec` / `Semantic` などの分類が実運用で迷わないかを検証する

### 3.3 型とデータモデル

- nullable の扱いを見直す
- timestamp / decimal / symbol / quantity などの表現を統一する
- venue 固有概念と将来共通化しうる概念を切り分ける

### 3.4 構造と依存関係

- project 分割と物理配置を再評価する
- `internal` に閉じられる実装詳細を減らさず適切に隠蔽する
- architecture enforcement を強め、層破りを防止する

### 3.5 利用者体験

- getting started を短くする
- private API 設定ミスを早期に検出できるようにする
- CLI / MCP / library の概念差を減らす

### 3.6 品質保証

- contract test / live test / adapter parity test の責務を整理する
- flaky な検証の影響を減らす
- `v2.0.0` の非互換点をテストと文書で固定する

## 4. 破壊的変更を許容する理由

- `v1.0.0` を固定点として履歴参照できるため
- 将来の `Unified` や cross-venue な設計余地を確保したいため
- 利用者にとって不自然な API を長く温存しないため
- adapter やドキュメントを含めて全体整合を取り直すため

## 5. 壊してよいもの / 壊すべきでないもの

### 壊してよいもの

- public surface の命名
- DTO / option / result の型設計
- project 構成の一部
- adapter の入力形や出力整形の一部
- ドキュメント導線

### 壊すべきでないもの

- layer の責務分離原則
- 障害解析可能な観測性
- private credential の秘匿原則
- endpoint contract の根拠なき曖昧化
- 変更理由を追跡できる文書統治

## 6. 優先順位の初期案

1. `v2.0.0` で是正したい breaking change 候補を列挙する
2. public API と error contract の違和感を棚卸しする
3. 型表現と責務境界を整理する
4. test strategy と adapter parity を再編する
5. migration guide のベースを作る

## 7. 成果物イメージ

- `v2.0.0` 方針文書
- breaking changes 一覧
- migration guide
- 更新後の `docs/spec.md`
- 必要に応じた `docs/cli.md` / `docs/mcp-server.md` 更新
- `v2.0.0` の contract を固定する test 群
