# 文書整備計画書（再検証版）

※ 本書は当時の計画を記録した文書であり、
※ **履歴資料（Archive）**として扱う。
※ 現在の運用判断・文書分類には使用しない。
※ 参照先は `docs/index.md` / `docs/process.md` / 各 Normative 文書とする。
※ 現在の Normative 区分は `docs/process.md` を正とする。

## 1. 目的（Why）

本計画の目的は、以下の 3 点に集約される。

1. **取引所仕様に起因しない差異を、文書と実装の両面で排除する**
2. **複数の正解が存在する設計領域において、1 つの正規形（Canon）を選択・固定する**
3. **文書量を増やさず、判断余地（揺らぎ）を最小化する**

本計画は「説明を増やす」ためではなく、
**将来の判断・再設計・再議論を不要にするための文書構成を確定する**ことを目的とする。

---

## 2. 基本方針（Principles）

### P1. 文書は「判断を固定するため」にのみ書く

* Why / How / 背景説明は原則書かない
* 読み手の理解補助を目的とした叙述は行わない
* **判断が分岐し得る点のみを条文化する**

### P2. 正本は常に一意

* 規範（Normative）は最小限に限定する
* 事実・履歴・経緯は規範に混入させない
* 規範間の相互参照は極力行わない

### P3. 揺らぎは「分類」で止める

* 差異を**禁止**する領域
* 正解が複数あるが**統一**する領域
* 取引所仕様により**不可避**な領域

を文書構造そのもので分離する。

---

## 3. 揺らぎ抑制モデル（全体像）

本プロジェクトにおける揺らぎは、次の 3 層で管理する。

### Layer A: 利用者保証（Guaranteed）

* ライブラリ利用者が**分岐を書かなくてよい**領域
* 差異が出てはならない
* 正解は常に 1 つ

→ **Contracts / Overview** にのみ記載する

---

### Layer B: 実装正規形（Canon）

* 複数の正解があり得るが、**1 つを選択し固定**する領域
* 実装方法・構造・責務配置
* 利用者には露出しないが、**取引所間の実装差異は許さない**

→ **TopSpec（Canon 節）** にのみ記載する

---

### Layer C: 取引所差異（Variation）

* 公式 API 仕様に起因する不可避差異
* 機能有無・制約値・精度・レート制限等

→ **Inventory / Allowed Variations / Exceptions** に限定する

---

## 4. 文書体系（最終形・正本構成）

### 4.1 Normative（拘束力あり）

1. **TopSpec**

   * 層・境界・依存方向
   * 実装正規形（Canon）
   * 差異吸収責務の固定

2. **Contracts**

   * 型・形状・意味論（Shape / Semantics）

3. **Contracts / Overview（新設）**

   * 利用者保証（Guaranteed）
   * 差異許容（Allowed Variations）
   * 利用者が分岐すべき／すべきでない点

---

### 4.2 Non-Normative（事実・運用）

4. **Inventory / Endpoints**

   * API の存在一覧（事実のみ）

5. **Exceptions Ledger**

   * 規範からの逸脱の唯一の記録先

6. **Process**

   * 文書運用・レビュー・例外登録手順

---

## 5. 作成・整備の順序（固定）

### Step 0（前提）

* 本計画書は、当時の合意に基づく **計画および検討過程の記録**である
* 以降の文書変更は本計画に従う

---

### Step 1（最重要）

**Contracts / Overview を新設する**

* Guaranteed（差異禁止）

  * 同名 Contracts API は取引所間で前提条件差を持たない
  * Symbol / Market / OrderKey の意味論は共通
  * NotSupported は capability 不足の場合にのみ許可

* Allowed Variations

  * 機能有無・制約値・取引所固有要素

→ 利用者視点における「落ち先」を確定する

---

### Step 2（Canon の確定）

**TopSpec の Canon 節を精査・固定する**

* Canon は「Guaranteed を実現するための標準実装形」と位置づける
* 正解が複数あり得る領域は 1 つに決める
* 選定理由（Why）は記載しない

---

### Step 3（Contracts 本体の純化）

**contracts/contracts.md を型規範に限定する**

* 利用者期待・運用判断は Overview に移動
* 型・Nullable・Page / Cursor 定義のみを残す
* 整形・変換・補助操作は Utilities に集約する

---

### Step 4（Inventory / Exceptions の再接続）

* Inventory は事実記録に徹する
* Guaranteed を破る必要がある場合のみ Exceptions に登録
* 差異がどの層に落ちるかを最終確認する

---

## 6. 完了条件（Done Definition）

以下をすべて満たした時、本計画は完了とする。

* 利用者が Contracts / Overview のみで

  * 差異が出ない領域と出る領域を判断できる
* 実装者が TopSpec の Canon に従えば

  * 取引所間の実装差異が発生しない
* 差異が発生した場合

  * 必ず Inventory または Exceptions に落ちる
* 「この判断はどこに書くべきか」という議論が発生しない
* Contracts に便利機能が残っていない
* Utilities に便利機能が集約されている

---

## 7. 割り切りと禁止事項

* 共通実装が 1 つしか存在しない箇所でも、
  将来複数実装が生じ得る場合は Canon に含める
* Canon において「最善」「推奨」といった表現は禁止
* 規範文書内に背景説明を追加することを禁止

---

## 8. 次のアクション

1. 本計画書を確定する
2. Contracts / Overview の章立てのみを作成する
3. 章単位で内容を確定し、他文書を追従させる

「新規追加か／移設か／現状維持か」を含め、整備方針を事前に固定する。
以降の作業では、本方針からの逸脱を行ってはならない。
