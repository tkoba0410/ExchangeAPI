# REVIEW-05: Cross-Exchange Parallelism / Symmetry Review

対象: `Bitflyer` / `Bittrade` の並列性・対称性

評価方針:
- 個人の好みではなく、将来の取引所追加・endpoint追加時の保守性と事故防止を優先
- 既存ドキュメント（TopSpec / parity policy / endpoint inventories）を基準に、実装差を「許容すべき差」と「揃えるべき差」に分離

---

## 結論（要約）

- **骨格（Wire/Raw/Normalized/Adapter + Public/Private + Internal）は概ね高い対称性を維持**できている。
- 一方で、**命名境界（インターフェース名の交換所プレフィックス有無）**と、**Adapter の公開面の分割粒度**に揺らぎがあり、将来追加時に「どれを正準とするか」の判断コストが増える。
- 機能差由来の非対称（Endpoint 群の差）は妥当。問題は機能差ではなく、**同じ責務に対する構造差の混入**。

---

## P0（優先度: 最優先 / 事故予防に直結）

### P0-1. 「同責務 API の命名境界」を全取引所で固定化する

現状:
- Raw / Normalized / Wire Internal で、同責務の I/F 命名が揺れている（例: `IRawApi` vs `IBittradeRawApi`, `INormalizedApi` vs `IBittradeNormalizedApi`, `IWireCallExecutor` vs `IBittradeWireCallExecutor`）。

リスク:
- 新規取引所追加時に「交換所名を付ける/付けない」が人依存になる。
- DI 登録・検索・コード生成・静的検証の規則が複線化し、誤配線・見落としの温床になる。

ルール化提案（揃えるべきポイント）:
- 交換所配下の層内 I/F 命名を **単一規則**に固定する。
  - 例A: 常に非プレフィックス（`IRawApi`, `INormalizedApi`, `IWireCallExecutor`）
  - 例B: 常に交換所プレフィックス（`IBitflyerRawApi`, `IBittradeRawApi`）
- どちらを採るかより、**全取引所で同一**であることを最優先にする。
- 逸脱時は `docs/exceptions.md` に期間付きで記録し、恒久化を禁止する。

---

## P1（優先度: 高 / 追加開発時の摩擦低減）

### P1-1. Adapter の公開面の分割単位（Facade 粒度）を統一する

現状:
- Bitflyer 側は Private 契約の写像ロジックが比較的一体にまとまっている。
- Bittrade 側は `Account / Trading / SpotHistory` などに分割され、束ね方が異なる。

リスク:
- endpoint 追加時に「どこへ実装すべきか」が取引所ごとに異なる。
- Contracts 変更時の横展開手順が統一できず、レビュー観点が増えて抜け漏れを誘発する。

ルール化提案（揃えるべきポイント）:
- Adapter の「Contracts 入口」だけは全取引所で同じ形（1クラス or 固定分割）にする。
- 内部委譲の分割は許容しても、**入口の見え方・責務境界**は揃える。
- 追加 endpoint 実装手順を「入口→内部委譲→mapper」の固定テンプレート化で運用する。

### P1-2. Internal 下位構造の許容差を明文化する

現状:
- `Raw/Internal` の下位構造（例: `Encoding` サブフォルダ有無）など、補助構造に差がある。

リスク:
- 取引所追加時に Internal 構成が無制限に発散し、保守時の探索コストが上がる。

ルール化提案（揃えるべきポイント）:
- Internal は「責務語彙セット（Encoding / Factory / Mapper / Resolver）」を定義し、
  **許可語彙以外の新設はレビュー必須**とする。
- 完全一致までは要求せず、**増やす理由の説明責務**を設ける。

---

## P2（優先度: 中 / 長期の認知負荷低減）

### P2-1. EndpointId 命名差（Method prefix有無）に対する“実装面の防波堤”を強化する

現状:
- Bitflyer は Path 由来中心、Bittrade は Method prefix を含む命名。
- inventory 上は整理されているが、実装側は命名差の影響を受けやすい。

リスク:
- 取引所追加時に EndpointId 由来のメソッド名規則が分岐し、命名監査が複雑化する。

ルール化提案（揃えるべきポイント）:
- `EndpointId -> *CallAsync` の機械検証を強化し、
  命名差は inventory で吸収、実装は自動チェックで収束させる。
- 新規取引所 onboarding 時に「EndpointId命名方式」を先に確定し、後追い修正を禁止する。

### P2-2. ExchangeInfo 以外の「取引所固有拡張点」の記録テンプレートを追加する

現状:
- ExchangeInfo は比較的整っているが、他の固有拡張点は散在しやすい。

リスク:
- 非対称が“意図されたものか偶発か”を後から判定できず、負債化する。

ルール化提案（揃えるべきポイント）:
- 非対称を導入する際の最小記録テンプレートを運用（理由/影響層/解消条件/代替案）。
- 「非対称の棚卸し」を定期化し、不要な例外を削減する。

---

## 揃えるべきポイント一覧（実務用）

1. 層内 I/F 命名規則（交換所プレフィックス有無）を単一化
2. Adapter の Contracts 入口の構造を単一化
3. Internal 下位語彙（Encoding/Factory/Mapper/Resolver 等）の許容範囲を定義
4. EndpointId 由来メソッド命名の自動検証を追加・強化
5. 非対称導入時の記録テンプレートを導入

---

## 非対称を許容する理由（整理）

許容してよい非対称:
- **取引所仕様差に起因する endpoint の有無・粒度差**
- **レスポンス shape 差に起因する DTO 差**
- **公式仕様の制約（認証方式・パラメータ体系・履歴 API 構造）**

許容すべきでない非対称:
- 同責務なのに命名規則だけ異なる
- 同責務なのに入口構造だけ異なる
- ルールで吸収可能なのに、取引所ごとの慣習で分岐している

判断基準（将来追加観点）:
- 新規取引所 `X` を追加するとき、既存2取引所のどちらを写経すべきか迷うなら、その差は原則「非許容」。
- 迷わない（仕様差として説明可能）なら「許容」。

---

## 次アクション（変更は行わない提案のみ）

1. 命名規則（I/F名）を governance へ追記し、例外運用を禁止
2. Adapter 入口の標準形を 1 つに固定（分割を採る場合も固定分割名を定義）
3. parity 監査チェックに「命名境界」「入口構造」を追加
4. 非対称記録テンプレートを docs に追加（運用開始）
