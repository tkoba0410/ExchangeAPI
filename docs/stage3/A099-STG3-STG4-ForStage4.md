# 次ステージ以降に回す内容（Stage3 デメリットからの抽出）

Stage3 デメリット（改善余地）のうち、**Stage3 ではなく、Stage4 以降に回すべき項目**を整理したドキュメント。

---

## ■ 1. 利用者視点のドキュメント整備（Stage4 以降）
Stage3 は内部基盤（POST 縦スライス）の確立が目的であり、外部利用者向けのガイドは必須ではない。以下は次ステージへ回す。

### ● 対応を後回しにする理由
- Stage4 以降で注文種類が増える（LIMIT / STOP / cancel など）ため、早期に HowTo を書くと後で更新が多発する。
- 現段階では SDK 内部の基盤が固まっていれば十分。

### ● 次ステージでやる内容
- Quick Start（例：MARKET 注文の使い方）
- よくある実装パターン（アカウント切替、CredentialProvider）
- API リファレンス整備（XML コメント→DocFX などで自動生成）
- サンプルコード集（コンソールアプリ・ユニットテスト）

---

## ■ 2. 文書量が多く新規参加者に負荷がある問題（Stage4 以降）
Stage3 文書（A010〜A090）は内部向けステージとしては適切だが、新規参加者への負荷は高い。これは Stage4 以降にまとめて対処するべき項目。

### ● 対応を後回しにする理由
- Stage3 は基盤レイヤの定義フェーズであり、どうしてもドキュメント量が増える。
- Stage4 以降で機能セットが揃ってから「総まとめ 1枚」を書く方が効率的。

### ● 次ステージでやる内容
- Stage1〜Stage4 の全体像を 1 枚で説明する資料（"Architecture Overview"）
- README.md の再構成（利用者向けと開発者向けの切り分け）
- "Entry Guide"（初見者向け最短ルート資料）の作成

---

## ■ まとめ
次ステージ以降に回すべき内容は次の 2 つ：

1. **利用者向けドキュメント整備（HowTo, API リファレンス, サンプルコード）**
2. **新規参加者向けの onboarding 改善（概要資料、README 再構成）**

これらは Stage3 の縦スライスに直接影響しないため、Stage4 以降にまとめて実施するのが最も効率的である。
