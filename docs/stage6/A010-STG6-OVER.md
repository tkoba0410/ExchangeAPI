# A010-STG6-OVER  
Stage6 Overview（REST-only 信頼性・運用強化ステージ / WS 廃止後の土台固め）

---

## 1. Stage6 の目的（OVERVIEW）

Stage6 は、Stage5 で完成させた **bitFlyer 向け REST-only ExchangeAPI** を、実運用に耐えるレベルまで引き上げるためのステージとする。  
もともとロードマップ上で Stage6 は「WebSocket/リアルタイム拡張」としていたが、**WebSocket は本ラインから正式に廃止**し、ExchangeAPI は **REST 専用ライブラリ** として継続する。

本ステージの主目的は次のとおり：

- Stage5 までに確立した REST-only 抽象 API（Market / Trading / Account / Margin / ExchangeInfo / RawApi）を、  
  **レート制御・リトライ・タイムアウト・サーキットブレーカなどの信頼性パターンで武装**する。
- ログ・メトリクス・トレースといった **運用・監視のためのフックを標準化し、ライブラリとしての「扱いやすさ / 見えやすさ」** を高める。
- エラー分類や設定インターフェースを整理し、**利用者が「安全なデフォルト」から始めつつ、必要な箇所だけを上書き可能な DX** を提供する。
- これらを **WebSocket や Realtime API を一切追加せずに達成する** ことで、REST-only の単純さと可読性を維持する。

---

## 2. 今までやったこと（Stage1〜5 の成果の整理）

Stage6 は、Stage1〜5 で積み上げた基盤の上に成り立つ。ここでは信頼性・運用強化の前提となるポイントだけを抜粋する。

### 2.1 Stage1〜3：REST と Private API 呼び出しパターンの確立
- Stage1: Public REST（Ticker/Board/Executions）と HTTP クライアント基盤を用意。
- Stage2: `/v1/me/getbalance` を通じて **Private GET + 署名付き REST クライアントパターン** を確立。`ExchangeApiException` による E1 エラー処理も導入。
- Stage3: `/v1/me/sendchildorder` を MARKET 注文で縦に通し、**Private POST のテンプレート** を確立。

### 2.2 Stage4：抽象 API の統合設計
- Market / Trading / Account / Margin / Realtime / ExchangeInfo の 6 区分を定義し、抽象インターフェースと最小ドメインモデルを整理。  
- Raw API 逃がし口の方針も明示し、以降のステージが迷わないような骨格を作成。

### 2.3 Stage5：REST-only bitFlyer 実装とフォルダ構成の確立
- Stage4 抽象 REST API を **bitFlyer 縦スライスで実装し、REST-only としての「最初の完成形」** を構築。  
- LIMIT/STOP/キャンセル、残高・証拠金・建玉取得など代表的トレードフローを end-to-end で通す。
- `Contracts / Transport / Factory / adapter/Bitflyer` のレイヤ分離と、API 区分と 1:1 対応したフォルダ構成（Market/Trading/Account/Margin/ExchangeInfo/RawApi）を整備。  
- WebSocket/Realtime に関するコードをライブラリ本体から除去し、**REST-only 方針を明文化**。

Stage6 は、この REST-only 土台とフォルダ構成を変更せず、上に **信頼性・運用のレイヤを積む** ステージとして位置付ける。

## 3. Stage6 でやること（スコープ）

### 3.1 信頼性パターン（Rate Limit / Retry / Timeout / CircuitBreaker）

- **レート制御**
  - 取引所の公式レートリミット情報を前提にした「推奨設定値」をドキュメント化。
  - `IHttpPolicy` など Policy 層で、固定間隔 / トークンバケット相当の簡易 RateLimiter を選択可能にする。

- **リトライ & タイムアウト**
  - `IRestClient` 呼び出しに対して、タイムアウト・リトライ戦略を設定できるようにする（例：ネットワーク一時障害のみリトライ、Idempotent GET のみ複数回許可）。
  - デフォルトは「安全寄り」の控えめなリトライにし、Factory からの上書きを許可。

- **サーキットブレーカ / フェイルファスト**
  - 一定時間内の失敗回数に応じたサーキットブレーカを導入し、バックエンド障害時にフェイルファストできるようにする。
  - 開閉状態はメトリクスやログで確認可能とする。

### 3.2 エラー分類の高度化（E1 → E2/E3）

- Stage2 で導入した `ExchangeApiException` を拡張し、以下のようなカテゴリに整理：
  - 認証・認可エラー（Unauthorized/Forbidden）
  - レートリミット超過
  - 一時的なネットワーク障害
  - 業務エラー（残高不足、注文サイズ不正など）
- bitFlyer 固有のエラーコード → ドメイン例外へのマッピングを整備する（例：`InsufficientFundsException` 等）。
- エラー分類の結果をログ・メトリクスに反映し、運用時の分析がしやすい形にする。

### 3.3 ログ・メトリクス・トレース（観測性 / Observability）

- **ログ**
  - `IRestClientLogger` を拡張し、RequestId / エンドポイント / 所要時間 / HTTP ステータス / 主要ドメイン属性（プロダクトコード等）を記録可能にする。  
  - 機密情報（APIキー / シークレット / 生リクエスト署名）はログに残さない方針を徹底。

- **メトリクス**
  - 呼び出し成功率、平均レイテンシ、エラー種別ごとのカウント、サーキットブレーカ状態などをメトリクスとして公開できるフック（インターフェース）を用意。
  - OpenTelemetry などへの橋渡しがしやすい形を意識する。

- **トレース**
  - コリレーション ID / トレース ID を受け渡す仕組みを検討し、上位アプリケーションのトレーサと連携しやすくする。

### 3.4 設定と Factory の DX 向上

- `BitflyerClientFactory` を中心に、以下のような DX を整える：
  - 「最小設定で動く安全なデフォルト構成」と、
  - 「信頼性パターン・ログ・メトリクスを細かく制御したい上級者向け構成」  
  を両立する API デザイン。

- 具体例：
  - `BitflyerClientOptions`（タイムアウト・リトライ回数・RateLimit 設定・ログ詳細度など）
  - `WithObservability(…)` のような拡張メソッドで外部モニタリングと簡単に接続できるフック。

### 3.5 テスト・検証（Fault Injection / Stress Test）

- レートリミット / ネットワーク障害 / 遅延などを模擬する **Fault Injection テスト** を整備し、信頼性パターンが意図通り動作することを確認。
- 代表的なトレードフロー（Stage5 の DoD で定義済み）に対して、**劣化環境下での結合テスト** を追加。
- 実環境への影響を避けるため、Paper Trading / Sandbox / ドライランモードの利用方針を簡単にガイドする（実装がなくても、少なくともドキュメントで推奨を示す）。

### 3.6 ドキュメント整備（OVR / QuickStart / 運用ガイド）

- 本書（A010-STG6-OVER）の他に、以下を整備：
  - 「信頼性パターンとデフォルト設定」の説明
  - 「ログ・メトリクスの取り扱い方法（サンプルコード付き）」
  - 「本番環境向け推奨設定例（低負荷 / 高頻度トレードなどシナリオ別）」
- STAGES-OVERVIEW における Stage6 の説明を **REST-only 信頼性・運用強化ステージとして更新**する。

## 4. Stage6 でやらないこと（スコープ外）

### 4.1 WebSocket / Realtime 機能（正式廃止）

- Ticker / Board / Executions 等の WebSocket ストリーム、および Realtime API は **Stage6 においても実装しない**。
- ライブラリ本体には WS に関するインターフェース・DTO・実装を一切含めない方針を維持する。
- 将来必要になった場合は、**別リポジトリ・別パッケージとしての独立モジュール** として検討する（本ステージのスコープ外）。

### 4.2 複数取引所対応

- Stage6 は bitFlyer の 1 取引所を対象とし、**信頼性と運用パターンが REST-only で十分かを検証するステージ** とする。
- Binance / Bybit 等、他取引所への横展開は Stage7 以降の課題とする。

### 4.3 高度な注文戦略・オーケストレーション

- IFDOCO / OCO / アルゴ注文、ポートフォリオ横断のオーケストレーション層などは扱わない。
- Stage6 の範囲は「既存抽象 API + 代表的トレードフロー」を **壊さずに強くする** ことに限定する。

### 4.4 大規模なドメインモデル変更 / ブレイキング変更

- 信頼性・運用の観点からやむを得ない場合を除き、**Stage5 で確定した抽象 REST API とドメインモデルに対するブレイキング変更は行わない**。
- 単純なフィールド追加やオプション設定の追加など、後方互換性を保てる形を優先する。

## 5. 評価・検証（メリット / デメリット）

### 5.1 Stage6 方針（REST-only 信頼性強化）のメリット

- **WS 廃止による責務の明確化と単純化**  
  REST のみで API 契約が固定され、抽象 API・フォルダ構成・型システムが一貫して扱いやすくなる。

- **保守性と可読性の向上**  
  ネットワーク層・Policy 層・Factory の構造を壊さずに信頼性パターンを追加でき、コードベース全体の複雑度が増えない。

- **信頼性パターンを REST に集中して最適化できる**  
  Retry / Timeout / RateLimit / CircuitBreaker を一つの統合層として設計でき、API 呼び出しの全体品質が向上する。

- **運用・監視が容易**  
  ログ・メトリクス・トレースが REST 呼び出しのみに集約され、監視対象・指標が明確になる。

- **Stage7 以降の他取引所対応がスムーズ**  
  REST-only 抽象 API が安定したことで、HTTP 呼び出し部分のみ差し替えれば他取引所向け adapter を実装しやすくなる。

### 5.2 デメリット / トレードオフ

- **リアルタイム性の欠如**  
  板更新頻度・約定反映の速度が REST Polling に依存するため、HFT や板監視アルゴ用途には不向き。

- **既存の WS を利用するユーザには適用領域が狭い**  
  取引所の WS 機能を使っているユーザに対しては、このライブラリ単体では不足が残る。別モジュールを必要とする可能性。

- **信頼性パターンの追加による設定項目の増加**  
  DX に配慮するが、それでも Timeout/Retry/RateLimit の設定が多少複雑になりうる。

- **Polling による API 消費量増加の可能性**  
  特に板・約定情報を頻繁に取得するワークロードでは、REST 呼び出し回数が増えやすい（RateLimit 管理で吸収可能だがトレードオフ）。

## 6. 完了条件（Definition of Done）（Definition of Done）

Stage6 は、次の条件をすべて満たした時点で完了とみなす。

1. **信頼性パターン**
   - RateLimit / Retry / Timeout / CircuitBreaker を構成可能な形で提供し、
   - デフォルト設定で通常の取引利用に十分な安全性が確保されている。

2. **エラー分類**
   - `ExchangeApiException` によるエラー分類が E2/E3 レベルに拡張され、
   - 代表的な bitFlyer エラーがドメイン例外としてハンドリング可能である。

3. **観測性**
   - ログ・メトリクス・トレース用のフックが整備され、
   - 少なくとも 1 つの「参考実装」または「サンプルコード」が存在する。

4. **DX / 設定**
   - `BitflyerClientFactory` 等から、信頼性/運用オプションを簡潔に構成できる。
   - 最小構成（デフォルト設定）で Stage5 と同等のフローが通り、追加設定で運用ニーズに応じたチューニングが可能である。

5. **テスト・検証**
   - Fault Injection と劣化環境下での結合テストが整備され、代表フローが成功する（残高→注文→約定確認→履歴→キャンセル→ポジション→証拠金を TestFactory/モック Transport で確認済み）。
   - Public/Private それぞれで簡易な負荷・レイテンシ計測が行われ、Timeout/Retry/RateLimit/CircuitBreaker のデフォルト値が計測結果を反映した形で確定している（現状は叩き台、計測反映は残タスク）。
   - DoD に沿ったテスト（ポリシー単体/劣化環境結合/観測性サンプル）が緑である。
