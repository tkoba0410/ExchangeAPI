# TopSpec.Guide

本書は TopSpec.Core を理解・運用するための補助であり、規範（ルール）を追加しない。
矛盾がある場合は TopSpec.Core を正とする。

---

## 方針

* TopSpec.Core は最小規範であり、詳細は Interfaces / Contracts / Inventory / Exceptions に委譲する。
* 本書（Guide）は「なぜそうするか」「誤用されやすい点」を短く補足する。

本書は短く保ち、詳細が必要になったら「要約＋参照」だけを残す。

---

## 0. 本書の位置づけと読み方（Core 前提）

* 本書は TopSpec.Core を前提として読む。
* 本書は Core の再解釈や上書きを行わない。
* 本書は「なぜそう決めたか」「どう誤用されやすいか」を記録する。

### 0.1 なぜ Core は短くあるべきか

* 憲法は短く、不変でなければ機能しない。
* 理由・背景・運用を含めた瞬間に、変更圧が Core に流入する。
* したがって Core は **規範のみ** を保持し、理解補助は必ず外部に置く。

---

## 1. 決定事項／非決定事項（Core §1 対応）

### 1.1 Core が決めること

* 境界・責務・依存方向・不変条件のみを決定する理由
* 仕様と実装の混線を防ぐための最小決定

### 1.2 Core が決めないこと

* 物理構成・運用・具体例を Core から排除した理由
* それらを Guide に置く必然性

---

## 2. 大原則の背景（Core §2 対応）

### 2.1 公開境界を明示する理由

* 境界が曖昧な API は破壊的変更を検知できない

### 2.2 層跨ぎ禁止の意味

* 層を跨ぐ責務混在が引き起こす破壊

### 2.3 不変条件を破壊的変更扱いとする理由

* 不変条件は利用者との契約そのものである

---

## 3. 変更の扱い

* 規範の変更は影響が大きい。必要性と影響範囲を明示して行う。

## 5. よくある誤用（短く）

- Raw に意味論（enum/既定値/妥当性検証）を入れない（→ Normalized）
- Normalized に横断抽象を入れない（→ Contracts）
- Inventory を仕様にしない（→ 公式文書が正本）
